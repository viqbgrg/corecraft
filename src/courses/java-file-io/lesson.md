## Problem · 完成复制，文件真的保存了吗

把 A中🙂B 加换行复制到新文件。应用按字节读取，字符可能跨多个字节；读取完成、输出缓冲清空、内核接收、设备持久化是不同事件。

## Why · Stream 接口隐藏了传输粒度

FileInputStream 是字节流，单字节 read 返回 0–255，-1 才表示 EOF。零字节是合法数据。字符需要 Reader 和明确编码，本课复制原始 UTF-8 字节，不在每次 read 上单独解码字符。

BufferedInputStream 先批量预取，再满足应用的一次一字节读取；BufferedOutputStream 将小写入合并。减少系统调用不等于同样减少物理磁盘访问，Page Cache 可能已经命中。

## Mechanism · 三层缓冲与资源生命周期

默认十字节源文件，四字节输入缓冲，三次读取数据加一次 EOF 检查，共四次教学 read 请求；无缓冲逐字节则十次数据请求加一次 EOF。两组读取的是完全相同字节。

输出缓冲满时交给内核页缓存，尾部不足一批时仍留在进程内。flush 刷出尾部；FileChannel.force(true) 请求将已到达文件层的数据与相应元数据持久化。force 无法看见还未 flush 的 Java 输出缓冲。

try-with-resources 保证正常或异常离开时尝试 close。输出流的正常 close 会刷新其缓冲并释放资源，但这不自动提供主机断电的持久性。实际工程还要正确处理 close 异常与 suppressed exception，本模型省略异常链。

## Experiment · 字节相同，成本和恢复结果不同

1. 默认复制直到 read 返回 -1。查看十个实际 UTF-8 字节、四次 read 和尾部两个输出缓冲字节。
2. 对照有缓冲与无缓冲读取，确认字节相同，read 次数为 4 与 11。
3. 先 force，稳定文件只有已到内核的八字节。再 flush，内核变为十字节，稳定文件仍是八字节。
4. 再 force，模拟断电，完整文本恢复，达到目标。
5. 重开一次，只 close 后断电，观察未 force 的数据不能按本场景假设恢复。修改源文本试验零字节、空文件和多字节字符。

## Conclusion · 接口成功要对应具体边界

模型假设本地存储正确兑现 force，断电丢弃未持久的页；不模拟实际设备缓存、文件系统日志、目录 fsync、并发文件修改或真实 IO 时延。

流适合顺序处理字节，缓冲改善调用成本。要求耐久性时要追踪数据在哪一层，并明确文件和目录的持久化协议，不能仅凭 flush 名字推断断电保证。
