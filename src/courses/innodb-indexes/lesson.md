## Problem · 一条记录为什么有两条查找路径

表包含 `id`、`region`、`amount`。主键是 id，另建索引 `INDEX idx_region(region)`。查询 `id=30` 与查询 `region=1` 都能用索引，但它们先到达的叶子保存着不同内容。

先预测：`SELECT id, region, amount ... WHERE region=1` 返回四行，需要几次按主键回表？把 amount 从投影中去掉后，匹配的四个 id 会改变吗？

## Why · 索引是存储组织，也有维护代价

InnoDB 是 MySQL 的事务存储引擎。Server 解析 SQL、选择计划、协调 Binlog；InnoDB 用 Buffer Pool 缓存页，管理索引、锁、版本与恢复。理解这一分工，才能把 SQL 计划中的一次访问对应到真正的数据布局。

聚簇索引让数据记录位于主键树的叶子。二级索引按另一列排序，并携带主键以定位完整记录。主键变宽会使大量二级叶项变大；增加索引也让插入、删除付出额外维护成本。有显式主键时优先使用它；没有合适主键时，真实 InnoDB 会选择合适的唯一非空索引或生成隐藏聚簇键。

## Mechanism · 二级叶项携带的是主键

初始主键为 10、20、…、90。聚簇叶项关联整行；二级树按 `(region,id)` 排序。region=1 的叶项是 `(1,10)`、`(1,30)`、`(1,60)`、`(1,90)`。

主键点查从聚簇根走到叶子，直接取出 amount。二级范围查先定位 region 的起点，再沿叶子链扫描；需要 amount 时，对每个命中主键调用聚簇树查找。覆盖查询只产生 id 与 region，amount 一栏明确显示未读取。

两棵树都执行真实的插入、分裂、删除与合并。删除使用待删记录原有的 region，即使当前表单的 region 已改变，也不会删除错误的二级键。重复主键被拒绝，两个索引必须始终包含同一组业务行的对应键。

## Experiment · 固定条件，只改变所需字段

1. 默认 id=30，执行当前索引查询，确认读取到 region=1、amount=300。
2. 把查询入口改为二级 region 范围查询，保留 region=1 和完整字段，执行。结果为四条记录，回表四次。
3. 点击“对比覆盖查询与回表”。两组匹配相同 id，覆盖组回表为零，完成目标。
4. 选择覆盖字段并逐步执行，观察轨迹只有二级树访问。改查 region=2，结果集合和工作量随真实数据变化。
5. 将 id 改成 25、region 改成 3，插入并观察两棵树。再把 region 改成 1 后删除 id=25，检查被移除的二级键仍是 `(3,25)`。

## Conclusion · 覆盖的是字段，不是所有现实成本

这是一张最多 12 行、两棵 4 阶树的逻辑模型。节点访问不是磁盘 IO；不模拟 16 KiB 页、Change Buffer、缓存命中、并发或日志。主键直接映射到叶子记录载荷，不使用堆表的物理 RID。

现实 InnoDB 的覆盖查询还可能为 MVCC 可见性检查访问聚簇记录。因此本实验的“零回表”只适用于省略 MVCC 的字段读取模型，不能据此保证生产查询永不访问聚簇页。
