## Problem · 同一个包为什么带着几种地址

A 发消息给另一个网络中的 C。数据中同时出现应用载荷、端口、IP 和 MAC；第一帧的目的 MAC 属于网关 R，IP 目的却属于 C。这不是地址不一致，而是它们分别回答“交给哪台最终主机”“本跳交给谁”“主机内交给哪个端点”。

## Why · 分层让通信职责可以分别实现

OSI 是七层参考模型，TCP/IP 是实际互联网协议栈的常见组织方式。两者没有强制一一对应，但可以用来理解职责。

| OSI 职责         | TCP/IP 常见归类   | 例子                             |
| ---------------- | ----------------- | -------------------------------- |
| 应用、表示、会话 | 应用层            | HTTP、DNS、编码与会话逻辑        |
| 传输             | 传输层            | TCP 字节流、UDP 数据报、端口     |
| 网络             | 网际层            | IP 寻址与路由、ICMP 控制消息     |
| 数据链路、物理   | 链路 / 网络接口层 | Ethernet 帧、MAC、介质上传输比特 |

TLS 通常位于应用协议与传输服务之间，不能机械地把参考模型当成真实代码模块边界。每层都对相邻层提供服务，并把自身需要的头部加入封装。

## Mechanism · 下一跳只负责这一段路

拓扑左侧为 192.0.2.0/24，A=.10、B=.20、R 左接口=.1；右侧为 198.51.100.0/24，R 右接口=.1、C=.20。A 按网络前缀判断：同网段直接交给目的主机，否则交给默认网关。

ARP 在本 Ethernet 链路广播询问下一跳 IP 对应的 MAC。去 C 时，A 询问的是 R 的 192.0.2.1。R 收到数据帧，去掉链路头，检查路由、递减 TTL，再在右侧链路解析 C 并添加新的 Ethernet 头。没有 NAT 时，端到端源 / 目的 IP 保持，逐跳源 / 目的 MAC 改变。

IP 提供尽力而为的数据报交付，不承诺可靠、有序或不重复。UDP 保留数据报边界，用端口分用，可靠性和重试需要应用定义。TCP 则提供可靠有序字节流，不保留应用消息边界。

Socket 是操作系统的端点接口。UDP bind 指定本地地址与端口，connect 不等于 TCP 式握手；TCP 连接通常按协议与两端地址 / 端口识别。此模型用 UDP 9000 或已建立 TCP 9000 接收载荷，TCP 的建立与重传由其他课程演示。

## Experiment · 从失败层级定位问题

1. 默认向跨网段的 C 发送 hello，逐步观察下一跳选择、两次 ARP、两帧的 MAC 与 TTL，直到 Socket 收到载荷。
2. 保留 ARP 缓存重新发送，观察 ARP 广播次数变为 0，数据帧仍需发送。
3. 改为同网段 B，只有一条数据链路，TTL 不经路由器递减。
4. 向本地不存在的 .99 发送，观察 ARP 无应答；向 203.0.113.20 发送，观察路由器无路由。
5. 跨网段初始 TTL=1 时在 R 丢弃；改错端口则主机可达，但 Socket 不匹配。比较 UDP 的 ICMP 端口不可达与 TCP RST。

## Conclusion · 这是可解释的小拓扑

地址均来自文档专用网段，MAC 是本地教学地址，没有任何真实网络请求。载荷最多 32 个 UTF-8 字节。模型不实现交换机学习、路由协议、MTU、分片、校验和、NAT、IPv6 或 ARP 老化；无防火墙与 ICMP 限速，错误响应在这里确定产生，现实网络可能静默丢弃。

定位问题时先找证据：下一跳是否可达、是否有路由、TTL 是否耗尽、传输端点是否存在，再检查应用协议。某一层成功不保证上层也成功。
