## Problem · 建立连接不等于确认身份

TCP 建立了连接，双方还算出了相同数字，但对方真的是你准备访问的网站吗？一个错误或中间转接的主体也可能与你协商出共享值。TLS 必须把身份、协商过程和数据保护连在一起。

## Why · 三个条件共同构成安全通道

密钥建立让双方得到可用于后续保护的秘密；身份认证把公钥绑定到预期服务；完整性验证确保握手参数和记录没有被偷偷替换。只有“会加密”不足以完成认证，证书看起来存在也不足以证明握手完整。

## Mechanism · 先用小数字解释关系

实验采用极小的教学 DH：公开 p=23、g=5，客户端持有 a，服务器持有 b。客户端发送 A=g^a mod p，服务器发送 B=g^b mod p。客户端算 B^a，服务器算 A^b，两者都等于 g^(ab) mod p。

默认 a=6、b=15，A=8、B=19，共享值均为 2。程序真的执行模幂运算，但这些小数字很容易被穷举破解，绝不是实际 TLS 的安全参数。

| 阶段                      | 必须解释的证据                                   |
| ------------------------- | ------------------------------------------------ |
| ClientHello / ServerHello | 协商参数与公开交换量，导出共享值                 |
| Certificate               | 信任根、预期主机名、有效期等身份条件             |
| CertificateVerify         | 对端证明拥有证书关联私钥，并将身份绑定到握手记录 |
| Finished                  | 确认握手记录与导出密钥的一致性                   |
| Application Data          | 验证完成后才能交付应用内容                       |

实际 TLS 1.3 的证书、CertificateVerify、Finished 等握手消息在 ServerHello 之后受到握手密钥保护。后续应用记录使用 AEAD，结合安全密钥交换、签名、HKDF 与记录序号等机制；不是直接拿 DH 数字做 XOR。

本模型将真实签名和 Finished 验证抽象为可检查的验证条件：认证记录与收到记录是否一致，双方共享值是否一致，以及 Finished 是否被改动。证书根名称是模拟的验证前提，不是“根名称相同就等于验签成功”的实现方法。

## Experiment · 先成功，再定位拒绝点

1. 单步完成默认握手，观察 A、B 与两边共享值，再尝试交付 hello。展示的 XOR 字节会被实际还原，但仅用于演示相同共享值的作用。
2. 对比四种证书情形，统一按 learn.example.test 和第 10 天验证。未知根、错误名称、到期证书分别失败。
3. 改用名称不匹配的证书，运行后共享值仍相同，身份验证却拒绝应用数据。
4. 恢复证书，选择“改动服务器公钥”，观察 CertificateVerify 阶段拒绝；改动 Finished 则在密钥确认阶段拒绝。
5. 恢复无改动，改动私有指数，重新观察共享值；成功运行并完成证书对照后达到实验目标。

## Conclusion · 数学演示与真实密码协议的边界

本实验只演示单次服务器认证握手，不实现完整 TLS 字节协议、真实 X.509 链验签、HKDF、AEAD、撤销检查、会话恢复、客户端证书或 0-RTT。小群 DH 与单字节 XOR 不具备实际保密性，不能用于传输真实敏感信息。

模型中的私有指数是供学习者查看的玩具输入，真实私钥不应公开。真实应用应使用维护中的 TLS 库与平台信任机制，不能因为连接成功或共享值相同就跳过证书和握手验证。
