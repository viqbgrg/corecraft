## Problem · 等一个连接，错过其他连接

程序阻塞在 FD 3 上，即使 FD 99 已收到数据，也不会自动把这次 read 改成读取 FD 99。另一种停滞更隐蔽：epoll ET 已通知可读，程序只读了一半，然后一直等待下一次通知，剩余字节却留在缓冲中。

## Why · 等待就绪与搬运数据要分开

阻塞 read 在暂无字节时让线程等待指定 FD；非阻塞 read 返回 EAGAIN，表示当前不能继续。单纯循环所有 FD 会浪费 CPU。IO 多路复用允许一次等待关注多个 FD，在就绪后再决定处理哪个连接。

就绪不等于完整应用消息到齐，也不负责代替应用读取。TCP 是字节流，消息边界需要应用协议解释；读写都可能只完成一部分。就绪之后状态也可能被其他线程改变，所以非阻塞 IO 仍有价值。

## Mechanism · 集合管理与通知语义

select 用 FD 集合及最大编号范围描述兴趣，常见接口受 FD_SETSIZE 等限制；poll 使用 pollfd 数组，避免固定编号位图的同类限制，但仍需扫描注册项。epoll 将兴趣集合保存在内核，以就绪集合返回事件，注册 / 修改和事件处理仍有成本。

LT（水平触发）可以在后续等待中继续报告仍然就绪的 FD。ET（边缘触发）不保证为上次留下的字节再次通知；应用通常使用非阻塞 FD，在收到通知后读到 EAGAIN，再回去等待。

不能把真实 Linux ET 简化成“只有空变非空才触发”：已有未读数据时，新的到达也可能产生事件，多次事件可能合并。本实验对每次新到达排队一个可合并通知，用它说明通知与剩余字节不同步。

## Experiment · 重现两种停滞

1. 默认 epoll ET，到达 abcd，检查一次就绪事件，再只调用一次 read。返回 ab，缓冲剩 cd。
2. 再检查一次就绪事件，观察返回 0 但缓冲仍有 cd。循环 read 到 EAGAIN，确认全部字节被读取；比较 select、poll 与 epoll 后完成目标。
3. 重置 ET 流程，在部分读取后再注入字节，观察新到达可以重新排队通知。
4. 切换 LT，部分读取后再次检查，FD 3 仍被报告为就绪。
5. 切换阻塞 read，空缓冲读取 FD 3，再让数据到达 FD 99。线程仍等待 FD 3；给 FD 3 送数据后 read 才返回。

## Conclusion · 复杂度与生产事件循环还需要上下文

实验使用 FD 3、40、99，各缓冲最多 16 个 ASCII 字节。所有就绪检查显式使用 timeout=0，返回当前结果，不实际等待。对比中的 100、3、就绪数量是按编号、数组、集合查找的示意，不是 Linux 的准确指令数，也不意味着 epoll 的总成本恒定为 O(1)。

没有模拟写就绪、EOF、错误、惊群、并发消费、EPOLLONESHOT、EPOLLEXCLUSIVE 或回调调度。生产 Reactor 还需要公平处理、背压、消息解码与异常路径，后续 Java NIO / Netty 课程会继续讨论。
