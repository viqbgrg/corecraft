## Problem · SQL 写的是结果，执行器选择过程

订单有 customer_id 和 amount，客户有 id 和 city。固定查询先过滤 `amount >= 50`，连接客户，按 city 分组计算 SUM 与 COUNT，再按 SUM 降序、city 升序排序，取 LIMIT 组。

同一结果可以由不同 Join 得到。性能判断需要知道实际比较、探测和构建了多少次，而不是只看“用了索引”。

## Why · 估计计划需要实际工作量验证

Optimizer 根据统计与 Cost Model 在候选路径中选择。EXPLAIN 本身只展示估计，不执行数据算子；EXPLAIN ANALYZE 则会实际执行支持的语句，应理解其运行影响。本课“执行完整 SQL 管线”提供真实小表的结果和计数，不宣称是某版本 EXPLAIN 输出的逐字段复刻。

初始历史统计只估计一条订单通过过滤，实际有八条。低基数下已有索引探测便宜；更多探测可能让一次构建哈希再探测更合算。更新统计不会改变订单，却会改变自动选择的计划。

## Mechanism · 每个算子改变什么

Filter 逐条检查 12 条订单。Nested Loop 对每条通过过滤的订单比较全部 6 个客户键；Index Lookup 使用预先存在的唯一客户索引，每条订单一次探测；Hash Join 本次构建 6 个客户键，再逐条探测。索引构建不属于本次查询成本，哈希构建属于。

教学成本为：扫描每行 1，键比较 1，索引探测 3，哈希构建和探测各 1。三条路径的成本都包含同样的订单扫描；分组与排序另行展示，不混入这张连接成本表。单位不是毫秒，JavaScript Map 是抽象索引接口，不代表 MySQL 的哈希性能常数。

GROUP BY 真正累加每个城市的金额和计数。ORDER BY 使用有界内存生成排序段，段内插入排序，再多路归并；所有比较均显式计数。默认三组、每段容量二，生成两段并模拟外排；容量六时只需一段。LIMIT 最后取有序前缀，不先截断订单或分组输入。

Filesort 表示额外排序而非文件必然落盘。本课显式生成外排段以解释溢出，不执行实际文件 IO，也不实现 MySQL 的 top-N、双路排序或临时表完整策略。

## Experiment · 先核对结果，再比较代价

1. 点击 EXPLAIN，确认执行步骤仍为 0，估计通过过滤为 1。
2. 执行完整 SQL 管线。八条订单连接后按城市聚合：杭州 200、上海 190、深圳 190，COUNT 分别 3、2、3；金额相同时按 city 升序打破并列。
3. 实际对比三种 Join。结果一致；Nested Loop 比较 48 次，索引探测 8 次，哈希构建 6 次并探测 8 次。
4. 更新 Join 选择率统计，重新执行并再次比较，自动计划从 Index Lookup 变成 Hash Join，完成目标。
5. 把排序段容量从 2 改成 6，重新执行，三组结果不变、排序段从 2 变 1、不再模拟落盘。最后把阈值改为 150，确认空输入不会生成虚假的聚合组。

## Conclusion · 按算子定位工作量

这是 MySQL 8 风格算子模型，限定固定模板与内连接。city 同金额时按 Unicode 字符值排序，不代表 MySQL 默认 collation。Nested Loop 是对照基线；现代 MySQL 支持哪些连接算法取决于版本和计划。未实现任意 SQL、NULL、外连接、多表重排、磁盘索引或并行执行。

分析现实 SQL 时，先比较估计与实际基数，再定位连接探测、分组规模和排序溢出。把 ORDER BY、GROUP BY 和 Filesort 分开解释，才能提出对应机制的优化。
