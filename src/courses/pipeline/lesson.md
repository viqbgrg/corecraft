## Problem · 部件为什么总在等待

假设每条指令必须依次经过取指、译码、执行、访存、写回五个阶段，每个阶段占一个周期。让四条指令逐条做完，需要 20 个周期。但第一条指令执行时，取指部件已经可以服务下一条指令。

## Why · 提高吞吐量

流水线把不同指令的阶段重叠起来。没有停顿时，第一条指令仍要经过五个周期，四条指令却可以在 **4 + 4 = 8 个周期**内全部完成。这提高了整体吞吐量，并没有把每条指令的延迟变成一个周期。

开始需要填充、结尾需要排空。实验中的 IPC = 已完成指令数 / 已经过的周期数，包含这些开销；不能看到“五级”就认为性能永远提高五倍。

## Mechanism · IF → ID → EX → MEM → WB

**IF** 取指；**ID** 译码与依赖检查；**EX** 运算；**MEM** 访问数据内存；**WB** 写回并完成指令。没有内存操作的指令也经过 MEM。

如果 ADD 要读的寄存器尚未准备好，前端保持 IF / ID，让 EX 出现一个气泡；较早的指令继续向 MEM / WB 推进。不能把整个流水线一起停住，否则结果永远不会产生。

**不转发**时，消费者等到生产者写回，在 ID 读到新值后才能进入 EX。**有转发**时，可以把较早指令已经计算出来的结果直接送给 EX。多个较早指令写同一寄存器时，必须使用最近的那次写入。

LOAD 的数据在 MEM 结束时才产生。紧接着使用它的 ADD，即使开启转发，仍有一次 **load-use 停顿**。转发不能传递尚未产生的数据。

## Experiment · 对同一段程序做三个对照

1. 保持默认 LOAD 示例，推进到周期 4。LOAD 在 MEM，ADD 留在 ID，EX 出现气泡，R1 仍是 0。
2. 推进到周期 5，R1 写回为 21，ADD 通过转发算出 42，但 R2 还没有写回。
3. 运行至结束，观察 R2 = 42、R3 = 63 和 Memory[0x11] = 63。点击“对比三种执行方式”：顺序执行 20 周期，无转发 14 周期，有转发 9 周期。
4. 切换“连续的数据依赖”，比较有转发时的零停顿；再切换“互不依赖的指令”，观察填充与排空。每次切换都会重新开始。

## Conclusion · 同时推进不等于没有依赖

本实验是单发射、顺序执行的五级教学流水线，使用 16 位无符号寄存器，ADD 按模 2¹⁶ 运算。指令和数据内存分离，访存固定一个周期；STORE 的源操作数在 EX 取得、在 MEM 写入，也要经过 WB 才计作完成。无转发时假设同周期先 WB 写入、后 ID 读取；有转发时使用上一周期的 EX / MEM 结果。

这里没有分支、Cache Miss、结构冲突、异常、乱序或真实硬件时钟。CPU 入门课的四个微步骤与本课的五级流水线采用不同的教学划分；本课周期用于比较同一模型内的执行方式，不是现实处理器的性能测量。下一课用独立模型观察控制流预测的代价。
