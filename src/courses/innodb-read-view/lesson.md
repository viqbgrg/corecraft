## Problem · committed 不等于对所有读者可见

行最初为 10。T2 写成 20，T1 此时建立 RR 快照，然后 T2 提交。T3 又写成 30 并提交。磁盘或缓冲中的最新行可能已经是 30，但 T1 的普通读仍可得到 10。

要解释它，不能只检查版本“现在是否已提交”，还要检查它在快照创建时处于什么位置。

## Why · 快照需要保留判断依据

MVCC 让普通读取使用历史版本，避免所有读者都阻挡写者。代价是保存 Undo 版本，以及为读取维护可见性边界。RR 的普通一致性读通常复用首次读取创建的视图，RC 每次语句创建新视图；BEGIN 本身不必等于 RR 快照创建时点。

UPDATE 与 SELECT FOR UPDATE 属于当前读，具有锁规则，见事务课及下一节索引锁。本课只操作普通一致性读，避免把两种读取混在一起。

## Mechanism · 按事务 ID 走版本链

每个版本包含值、DB_TRX_ID 与指向旧版本的 Undo 指针。Read View 保存 creator、活跃集合 m_ids、最小活跃 ID `m_up_limit_id`，以及当时下一个可分配 ID `m_low_limit_id`。名字中的 up / low 容易混淆，应使用具体不等式。

按顺序判断：自己的写入可见；版本 ID 小于 up 边界可见；大于等于 low 边界不可见；处于边界内但在 m_ids 中不可见；边界内且不在活跃集合中可见。遇到不可见版本，沿 Undo 指针继续，直到找到第一条可见版本。

本模型每次 BEGIN 都分配教学事务 ID，因此可观察到 T2=1、T1=2、T3=3。真实 InnoDB 对只读事务的 ID 分配有优化。单行一次只允许一个活跃写者；冲突修改被拒绝，结束写者后需要手动重试。

Purge 不仅保留最新已提交版本，还保留各 RR 视图需要的完整链前缀。RC 语句结束后不会继续阻挡清理，界面中的最近视图仅作证据展示。活跃写者的回滚基线也必须保留。

## Experiment · 两种不可见原因与一次版本回收

1. 选择 T2，BEGIN 并写入 20，暂不提交。
2. 选择 T1，BEGIN 并普通读，得到 10。视图为 creator=2、m_ids=[1,2]、up=1、low=3。
3. 切回 T2 提交。再选择 T3，BEGIN、把新值设为 30、写入并提交。
4. T1 再普通读。版本 30 因 ID≥3 被排除；20 因 ID=1 在旧 m_ids 中被排除；初始版本 10 可见。
5. 点击 Purge，三版本仍保留。提交 T1，再 Purge，只剩 30，清理两条旧版本，完成目标。
6. 重置后选择 RC 重做两次读取，验证语句间提交会进入新的视图；也可试写后回滚，检查链指针没有悬空。

## Conclusion · 长快照会留下存储成本

模型按单行版本链精确保留教学读者需要的前缀，不模拟 Undo 页、History List、多个回滚段或后台线程。保留逻辑比真实全局 purge 更小，但能说明一个关键因果：旧视图还在，旧版本就不能随意删掉。

参考 [InnoDB 多版本机制](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)。排查历史版本增长时，既要看写入速率，也要检查未结束的读取事务。
