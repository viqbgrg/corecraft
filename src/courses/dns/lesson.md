## Problem · 不能让一个服务器记住所有名字

互联网的名字由不同组织维护，记录会改变，查询也很多。既要分散管理，还要让任何查询者找到负责这个名字的人。

## Why · 管理权逐层委派

DNS 的树形命名空间把职责拆开：根知道顶级域的服务器，顶级域知道下一级权威服务器，权威服务器维护最终记录。**转介告诉你应该问谁，不一定直接给目标 IP。**

以 `www.corecraft.test` 为例，命名层次从右往左展开：根、test、corecraft.test，再到具体名称。这里的 .test 是隔离的教学域，实验为它构造了一组服务器，不会向公共 DNS 请求这个域名。

查询还要说明记录类型。本课只问 **A 记录**，即名称对应的 IPv4 地址；AAAA 对应 IPv6，NS 指定负责某个区域的名称服务器，CNAME 指向另一个名称。DNS 不处理 URL 的路径、查询参数或业务内容。

## Mechanism · 递归解析器代你完成迭代

Browser / Stub 把请求交给 Local DNS（本课指递归解析器）。递归解析器分别询问 Root、TLD、Authoritative，并跟随转介；根不会替浏览器直接去问所有下游。

有效缓存让解析器跳过上游查询。TTL 到期需要刷新。NXDOMAIN 表示名称不存在，也能按权威的负缓存信息暂存。

### 谁负责继续提问

| 角色           | 收到请求后做什么         | 本课返回什么                  |
| -------------- | ------------------------ | ----------------------------- |
| Browser / Stub | 向递归解析器请求结果     | 等待最终答案                  |
| Local DNS      | 跟随转介，向上游逐次查询 | 最终记录或否定答案            |
| Root           | 指出顶级域由谁负责       | .test 的 NS 转介              |
| TLD            | 指出子区域由谁负责       | corecraft.test 的权威 NS 转介 |
| Authoritative  | 回答自己负责的区域       | A 记录或 NXDOMAIN             |

“递归”描述客户端要求解析器替自己完成解析；“迭代”描述解析器收到转介后继续问下一台服务器。观察箭头会发现，询问 Root、TLD、Authoritative 的发起者始终是 Local DNS，而不是 Root 一路替客户端问下去。

本课冷查询有三次上游提问。把请求与响应分别显示，再加 Browser 与 Local DNS 的往返，共有八条消息。图中的八步是教学拆分，不是八次独立上游查询。

### TTL 限制的是这份缓存能用多久

默认名称返回 `203.0.113.42`，TTL 为 60 s。若 t = 0 收到并缓存答案，t = 30 时剩余 30 s，仍可使用；t = 60 时已过期，不能再当作有效缓存回答。**命中一次不会把到期时间重新延长到 60 s。**

TTL 给缓存的陈旧程度设置上限，不是网络请求的超时时间。权威记录改变后，旧缓存也不会自动同步更新；在其有效期内，不同解析器可能仍持有不同时间取得的记录。本模型不提供修改权威记录的按钮，但 TTL 实验能说明为何需要这条规则。

对不存在的 `missing.corecraft.test`，权威回答 NXDOMAIN，模型保存 30 s 负缓存。它表示“确认名称不存在”，与超时没有收到答复、SERVFAIL 解析失败、名称存在但没有所问类型的记录是不同情况；本课实际操作的是 NXDOMAIN。

## Experiment · 相同问题，不同路径

1. 重置，保留 `www.corecraft.test`，从“开始查询”逐步点到“返回 Browser”。预期最终地址为 203.0.113.42，“本次上游查询”为 3，剩余 TTL 为 60 s。
2. 点击“再查一次”，再返回 Browser。此次只有应用请求和缓存响应，上游查询为 0。完成冷查询和同域名缓存查询后，实验目标达成。
3. 点击“时间 +30 s”，再次查询，仍命中缓存，剩余 TTL 为 30 s。再推进 30 s，TTL 为 0；下一次查询必须重新走上游，取得新答案后 TTL 才恢复为 60 s。
4. 切换到 `missing.corecraft.test`，完整查询后得到 NXDOMAIN，TTL 为 30 s。立即再查，仍然返回 NXDOMAIN，但上游查询为 0；推进 30 s 后重查，上游查询恢复为 3。
5. 选做：切换 `api.corecraft.test`，完整查询得到 203.0.113.10。说明“同属 corecraft.test”为什么不等于“可以复用 www 的最终 A 记录”。

每轮记下 **名称、时刻、结果、剩余 TTL、上游查询次数**。缓存命中改变的是获取答案的路径，既可以缓存成功答案，也可以缓存有期限的否定答案。

## Conclusion · 缓存与委派一起支撑规模

这里使用隔离的 .test 教学域与文档示例地址，不进行真实 DNS 请求。只缓存最终记录，省略 NS / glue 缓存、CNAME、DNSSEC、浏览器和 OS 的独立缓存，以及 UDP / TCP 传输细节。

自检：DNS 已返回 IP，能否证明网站能打开？还不能，TCP 建连、TLS 身份验证和 HTTP 应用处理都可能随后失败。接下来的 HTTP 课程会把这些步骤串起来。
