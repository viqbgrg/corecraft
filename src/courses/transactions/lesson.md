## Problem · 一次事务不只包含一个时间点

T1 读到库存 10，T2 将库存改为 20 并提交，T1 再读仍然是 10。T1 随后执行库存加一，却可能把当前值改成 21。要解释这种行为，必须区分普通快照读、当前读、自己的未提交写入和事务隔离规则。

## Why · ACID 不是一个万能开关

| 目标               | 需要解释的机制                             |
| ------------------ | ------------------------------------------ |
| 原子性 Atomicity   | 多行写集共同提交，回滚撤销未提交影响       |
| 一致性 Consistency | 数据库约束与应用定义的业务不变量           |
| 隔离性 Isolation   | 并发事务能观察哪些版本，哪些操作等待       |
| 持久性 Durability  | 成功提交在承诺的故障模型下能恢复，参见 WAL |

“一致性”不会自动替应用发明正确的业务规则。本模型约束库存为 0–200，非法更新被拒绝；如果业务还有跨行总量规则，需要另外实现。这里用版本和锁讨论并发，持久化由 WAL 课单独解释。

## Mechanism · 版本选择与锁协调

每个事务有私有写集，COMMIT 把其中多行以同一个提交序号共同发布。ROLLBACK 丢弃整个私有写集。已提交版本保留，读者可以按提交序号选择旧版本。

| 普通读取规则        | T2 未提交时                    | T2 提交之后                |
| ------------------- | ------------------------------ | -------------------------- |
| RU                  | 可以读到 T2 未提交值，产生脏读 | 可以读到新提交值           |
| RC                  | 读取该语句开始时已提交版本     | 下一条读取可以看到新值     |
| RR                  | 首次普通一致性读创建快照并复用 | 继续读取快照内版本         |
| Serializable 点读取 | 用 S 锁协调，写入的 X 锁会等待 | 等待释放后才能完成冲突写入 |

本课 RR 的 UPDATE 与 SELECT FOR UPDATE 按 InnoDB 风格使用当前读，加 X 锁；普通读取则遵循快照。自己的写入可见，因此不能简单说“RR 中所有操作永远看同一个旧值”。其他数据库的 RR / Snapshot Isolation 可能采用不同冲突处理规则。

行锁保护写写冲突。`库存 = 库存 + 增量` 在持有 X 锁后读取当前值，等待结束后重试也使用新的当前值。若应用先普通 SELECT，再把旧值加一后用绝对值 UPDATE，即使每次 UPDATE 都加锁，仍可能覆盖另一事务的更新。

S 锁之间兼容，X 锁与其他事务的 S / X 锁冲突。一次等待不是死锁；等待关系形成环才是。模型可以检测环，回滚编号较大的参与者，再让剩余语句重试。

## Experiment · 自己安排交错

1. T1 默认 RR，BEGIN 后普通读取行 1，得到 10。
2. 切换 T2，BEGIN、设置库存 20、COMMIT。再回 T1 普通读取，仍得到 10；当前锁定读得到 20。
3. 对比四种事务隔离规则，检查同一组读写顺序的差异。已经实际读取并提交过写事务后，完成实验目标。
4. 另开实验，用两个会话分别更新行 1 和行 2，再相互更新对方锁住的行，形成等待环。检测并回滚牺牲者，切回存活事务重试等待语句。
5. 测试多行修改后 ROLLBACK，以及负库存的 CHECK 约束拒绝。锁释放后等待语句仍需显式重试，模型不会替你偷偷执行它。

## Conclusion · 隔离级别需要具体到实现与语句

固定两行、两个会话，事务可按序重新开始；不模拟范围查询、插入、幻读、谓词锁、Gap / Next-Key Lock、版本清理或事务日志持久化。Serializable 只实现这个固定行集合上的两阶段锁，不能由此推断所有数据库的可串行化策略。

事务读写规则、索引访问范围、锁粒度和数据库实现共同决定结果。MySQL 课程将进一步把 Read View 的活动事务集合和范围锁对应到具体机制。
