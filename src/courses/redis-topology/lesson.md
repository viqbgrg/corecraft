## Problem · 服务恢复与写入保留不是同一结果

主节点确认一次写入，副本还没收到。主节点隔离后，Sentinel 提升副本提供服务。新主从已有历史继续，无法凭空恢复旧主尚未复制的写入。

## Why · 复制组与分片路由分别建模

Replication 复制一个数据历史以提高可用性和读取能力；Sentinel 监控并协调非 Cluster 复制组的主切换。Redis Cluster 把键按槽分配给分片，并有自己的集群故障机制。本课两个场景相互独立，不把 Sentinel 当作 Cluster 的控制平面。

## Mechanism · 多数授权与旧主分叉

复制组 M、R1、R2 异步推进。三个 Sentinel 在本场景使用 quorum=2，且故障转移需要多数授权；真实故障判断 quorum 与选举多数是不同条件，这里数值恰好相同。

M 与多数节点隔离后，另一路客户端仍可到达 M。Sentinel 不能仅凭判断远程强制停止旧主写入。提升相同优先级中最前副本后，链路恢复，旧主重配为副本并接受新历史，分叉写入被舍弃。WAIT 可增加写入被副本确认的证据，但不能把 Redis 自动变成强一致共识系统。

Cluster 对键或第一个有效非空花括号 tag 计算 CRC16/XMODEM，再模 16384。迁移中源节点仍拥有槽，键已经移走时可返回 ASK；目标在 ASKING 后接受该次请求。槽正式交接后，旧缓存请求得到 MOVED，需要更新映射。相关多键操作通常要求同槽，hash tag 可以帮助安排。

## Experiment · 复制组丢失与分片迁移

1. M 写入后先读取 R1，观察滞后；再把历史复制给 R1。
2. 隔离 M，再让隔离客户端写 M。S1 投票并尝试提升，尚不满足多数；S2 再投票后提升 R1。
3. 恢复链路，把 M 重配为副本，检查哪次已确认写入不在获胜历史中。
4. 在独立 Cluster 场景开始迁移槽，移走唯一教学键，按旧缓存 GET 得到 ASK。ASKING 重试成功，缓存仍指向源。
5. 发布新槽归属，再 GET 得到 MOVED，刷新缓存重试，达到目标。比较两键 hash tag 对槽号的影响。

## Conclusion · 高可用不是统一的一项保证

本课省略 Sentinel 超时与完整选举消息，候选优先级相同且可达。Cluster 只迁移单键槽，不模拟 gossip、Cluster 自身主切换、脚本或多键事务。

评估 Redis 系统时，分别询问谁服务请求、谁保存哪份历史、键该路由到哪里，以及分区后能否丢失已确认写入，避免用“有副本”代替这些具体保证。
