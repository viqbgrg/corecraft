## Problem · 一次请求，包含不同的问题

名字要转换成地址，传输需要连接，身份与内容需要保护，应用还要处理业务。只有把这些职责分开，才能解释一次等待或失败发生在哪里。

## Why · 分层让职责可以组合

DNS 解决“去哪里”，TCP 提供可靠字节流，TLS 为字节流提供安全保护，HTTP 表达应用请求与响应。一次 HTTP 500 与一次 TCP 超时发生在不同层，排查方向也不同。

以一个 HTTPS 请求为例，知道服务器地址不等于连接已建立；连接建立不等于身份已验证；安全通道可用也不保证业务处理成功。每一层为后续工作提供条件，观察失败时要找到最后完成的阶段和第一个失败的阶段。

## Mechanism · 从 URL 到应用数据

本模型采用 HTTP/1.1 over TCP。HTTPS 经历 DNS → TCP → TLS → HTTP → Server → Response；http:// 跳过 TLS。TLS 用抽象的 1.3 完整握手表示。

同源存活连接能复用 TCP 和 TLS，甚至不需要重新解析 DNS。只有 DNS 缓存则仍需建立新连接。模型将连接按 origin 隔离，不会把其他站点的连接随便拿来用。

### URL 的哪些部分会发送出去

把请求 URL 改为 `https://corecraft.test/hello?name=Lin#intro`，各部分的作用是：

| 部分     | 示例           | 作用                           |
| -------- | -------------- | ------------------------------ |
| scheme   | https          | 本课据此决定是否经过 TLS       |
| host     | corecraft.test | DNS 查询主机名，HTTP 携带 Host |
| path     | /hello         | 指定应用资源路径               |
| query    | ?name=Lin      | 随请求目标发送给服务器         |
| fragment | #intro         | 留在客户端，不随 HTTP 请求发送 |

本模型会发送的请求行是 `GET /hello?name=Lin HTTP/1.1`，并携带 `Host: corecraft.test`。GET 是请求方法，路径与查询参数构成请求目标；请求头补充元信息。响应则包含状态码、响应头和响应体，例如 HTTP 200、`Content-Type: application/json` 与 JSON 数据。

这里的 HTTP/1.1 格式用于展示报文含义。HTTPS 把 HTTP 报文放进 TLS 保护的通道中，客户端仍会看见解密后的 HTTP 状态和内容。

### 缓存映射和复用连接省去不同工作

origin 由协议、主机与端口共同确定。相同 origin 下换一个路径，仍可能使用原连接；从 https 改成 http、改主机或改端口，就不是同一 origin。本课 DNS 缓存按主机名保存，连接则按 origin 保存。

| 场景                    | 还需要做的准备         | 默认模拟总耗时 |
| ----------------------- | ---------------------- | -------------- |
| 首次 HTTPS 请求         | DNS 解析、TCP、TLS     | 225 ms         |
| 同源存活连接复用        | 不再做上述准备         | 85 ms          |
| 关闭连接但保留 DNS 缓存 | DNS 缓存查询、TCP、TLS | 206 ms         |

首次请求的 225 ms 来自 `20 + 60 + 60 + 30 + 25 + 30`：DNS、TCP、TLS、发送请求、应用处理、接收响应。复用后仍有后面 85 ms 的工作；连接复用不等于缓存了 HTTP 响应，也不等于服务器不再处理请求。

### 失败需要按阶段解释

| 注入故障        | 本模型停在哪里   | 是否收到 HTTP 响应 |
| --------------- | ---------------- | ------------------ |
| DNS 解析失败    | 无法取得地址     | 否                 |
| TCP 连接超时    | 无法建立连接     | 否                 |
| TLS 证书错误    | 安全协商失败     | 否                 |
| Server 返回 500 | 应用返回错误结果 | 是，状态码为 500   |

500 表示收到了一个报告服务端错误的 HTTP 响应，不能把它当成“TCP 没连上”。反过来，DNS 或 TLS 阶段失败时，本模型根本还没发送 HTTP 请求，也就没有应用状态码。

## Experiment · 找出可以省去的工作

1. 重置，保留默认 HTTPS URL、开启 Keep-Alive、使用 DNS 缓存和正常请求。点击“发起请求”，逐步推进到 Response，预期状态 200、连接 NEW、总耗时 225 ms。
2. 再发一次并推进到底，预期连接 REUSED、DNS / TCP / TLS 标为复用、耗时 85 ms。一次新连接请求与一次成功复用都完成后，实验目标达成。
3. 点击“关闭连接池”，再次请求。DNS 缓存仍有效，但 TCP 与 TLS 重新执行，总耗时为 206 ms。解释它为什么介于前两次之间。
4. 改为 `https://corecraft.test/hello?name=Lin#intro`，完成请求，检查日志：同源连接仍可复用，HTTP 请求目标包含查询参数，不包含片段。再改为 `http://corecraft.test/hello`，观察新 origin 需要新连接，TLS 被跳过。
5. 选做故障定位：恢复 HTTPS URL，依次选择 DNS、TCP、TLS 故障和 Server 500，每次都从新请求推进到停止或响应。注入故障会清空现有连接，DNS 故障还会清空解析缓存，使请求实际经过故障阶段。对照上表记录最后完成的层。

用 **URL、连接是否复用、经过 / 跳过的阶段、总耗时、响应或失败原因** 组织观察记录。比较耗时时保持 URL 与故障条件相同，单独改变连接或缓存条件。

## Conclusion · 耗时来自路径，也来自每层工作

所有数据与毫秒都是教学模拟，不执行 fetch、真实 DNS 或真实 TLS。DNS 缓存在本课中不计 TTL（TTL 见 DNS 课）；省略 HTTP/2、多路复用、HTTP/3、TLS 会话恢复、代理和子资源加载。每一层都是后续实验的入口。

自检：第二次请求的 DNS 阶段显示复用，是不是 TTL 变长了？这里利用的是已经建立的连接，无需再次找地址。再想想收到 500 时应该优先检查哪一层：应用日志和服务端处理是起点，而不是重新解释三次握手。
