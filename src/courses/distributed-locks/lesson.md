## Problem · 过期不等于旧线程消失

T1 获得三秒租约后暂停。服务端时间继续，租约过期，T2 得到新租约并写入资源。T1 恢复时仍保存旧 token，可能继续之前准备的写入。

## Why · 获取锁只是协调协议的一部分

分布式锁常用有限租期避免持有者故障后无限占用。释放需要在服务端原子比较 token 再删除，不能先 GET 再 DEL，否则两次操作间可能换了 owner。续租同样需要身份校验与有效期判断。

即使租约服务的获取和释放都正确，客户端暂停、延迟和超时仍可能让旧工作晚到。仅靠客户端“我之前拿到了锁”不足以保护资源。

## Mechanism · 将顺序约束交给资源

本服务每次成功获取分配单调 token。受保护资源保存已接受的最大 token，写入时原子比较，拒绝更旧请求。新 owner 的 token=2 已生效后，旧 token=1 无法再覆盖数据。

Fencing 本身不会检查租期是否仍有效。如果旧 token 已过期，但资源还没有看见更大 token，仅凭 token 比较可能仍接受它。这项协议防止旧 owner 覆盖已生效的新 owner，不是独立的时间授权检查。同 token 的重复业务也仍需要幂等设计。

生成 token 的协调服务和资源端比较都必须可靠；如果资源不支持检查，调用者不能仅在文档里声称已具有 fencing 保证。Redis 异步主切换还会引入另一类锁安全问题，本课不模拟它。

## Experiment · 重放完全相同的暂停顺序

1. 无 fencing 场景，T1 获取租约后暂停，服务时间推进三秒。
2. T2 获取 token=2，把资源写为 20。
3. T1 恢复，尝试释放，compare-and-delete 拒绝删除 T2 的租约；但携带旧 token 写 99 仍被无保护资源接受。
4. 切到资源端 fencing 的新场景，重复相同步骤。T1 的写入被拒绝，资源保留 20，达到目标。
5. 单独试验过期续租失败，以及资源尚未见更大 token 时的边界。

## Conclusion · 锁安全最终体现为资源接受规则

模型假设可靠租约服务、统一服务时钟、单调且不回绕的 token，资源可原子比较和写入。不实现 Redlock、时钟漂移、共识内部或真实服务故障。

设计分布式锁时同时描述获取、续租、释放、暂停恢复、资源 fencing 与业务幂等。缺失其中任何一项，都可能让“同一时刻一个锁记录”无法推出业务操作互斥。
