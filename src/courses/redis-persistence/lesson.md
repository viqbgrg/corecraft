## Problem · 成功回复之后的断电

INCR 返回 1，随后主机断电。是否恢复为 1，取决于当前使用的 RDB/AOF 策略以及稳定文件已覆盖到哪里，而不只取决于客户端是否收到成功。

## Why · 快照和日志保存不同证据

RDB 保存某一时间点的数据状态，适合紧凑恢复与备份。AOF 保存可重放的写入历史，fsync 策略决定稳定前缀推进方式。两者同时启用时，Redis 通常优先使用更完整的 AOF 恢复。

## Mechanism · 快照一致性、确认与重写

BGSAVE 开始时固定逻辑快照，父进程继续处理写入。实际 fork/COW 可以让子进程保留旧页视图，修改会产生额外内存成本；本模型用快照副本和写入证据表示，不复刻页分配。

AOF everysec 让写入先到 OS 文件缓存，稍后同步；典型故障窗口约一秒，但磁盘、调度和系统行为使它不能被解释成任何环境下严格的一秒上限。always 在本课每次 fsync 成功后才确认。存储仍必须正确兑现同步，配置名字不替代硬件保证。

重写从当前状态生成等价基线，同时保留其后的增量。新文件稳定后原子切换；若切换前断电，仍用旧稳定 AOF。本课把 INCR 的效果保存为等价 SET，避免重放时重复加法副作用。真实 Redis 版本可能使用多段 AOF 与 RDB 基线等格式。

## Experiment · 三种策略的相同写入

1. RDB 模式 INCR 到 1，开始 BGSAVE，再 INCR 到 2，完成快照。断电并恢复，值为 1，一次已确认写入未恢复。
2. 新 everysec 场景，INCR 后先不 fsync，断电恢复为 0。
3. 新 always 场景，INCR 后断电，恢复为 1，达到目标。
4. everysec 场景多写几次并 fsync，开始重写，再插入新写入，完成新 AOF 切换后恢复，确认基线和增量都在。
5. 对照重写未完成就断电，检查仍由旧文件稳定前缀决定恢复结果。

## Conclusion · 耐久性需要明确故障模型

实验只含一个 counter，断电丢弃所有未持久 OS 页，不模拟进程崩溃仍保留内核页的另一种故障。没有真实 fork、磁盘写坏、校验修复或完整 Redis 文件格式。

按恢复点、可接受数据损失、同步成本、重写资源和备份需求选择策略；复制提升可用性，但也不会自动替代持久化与备份。
