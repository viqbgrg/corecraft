## Problem · 等全部完成，还是限制同时进入

三个任务分别产生 10、20、30，协调者需要等三份结果。另有三个资源任务共用两个连接，同时最多运行两个。两种需求都有等待和计数，但计数的含义不同。

## Why · 高层同步器表达业务约束

CountDownLatch(3) 表示尚欠三个完成信号。每次 countDown 减一，到零后所有合适的 await 可继续。同一实例不能 reset。Semaphore(2) 表示两个当前可用许可，acquire 消耗一个，release 归还一个，可反复循环。

二者通常都借助 AQS 的共享同步能力，但共享模式不意味着同一业务协议。

## Mechanism · 发布顺序与许可守恒

完成任务先写结果，再 countDown。countDown 之前的动作经相关成功 await 建立 happens-before。本模型单独记录这些有效发布，避免提前数到零、后来才补结果也被误判为正确学习目标。Latch 不检查你的业务是否真的成功；异常路径也需要明确定义何时 countDown。

资源任务成功 acquire 后才进入 active，结束时在 finally 中 release。正常协议维持 active + available = 2。公平普通 acquire 在许可释放后允许队首等待者重新尝试，并不代替它执行任务。

Semaphore 没有独占锁的 owner 规则，可以由另一线程 release。它也不知道外部资源的实际容量，无配对 release 会增加可用许可。实验任务包装器禁止同一任务重复占用和无配对正常归还，这些是包装器约束，不是 Semaphore API 自带限制。

## Experiment · 两条独立协调路径

1. 协调者 await，进入等待。依次选择 T1、T2、T3，完成各自 Latch 工作。
2. 计数到零后再次调度 await，读取结果 [10,20,30]。再次 countDown，计数保持零；需要另一轮工作时创建新实例。
3. 依次让 T1、T2、T3 acquire。前两个占用资源，第三个等待。
4. T1 完成并 release；T3 重试获取，再依次完成 T2、T3。全部归还后许可为 2，目标完成。
5. 独立重开后直接额外 release，让三个任务都进入，观察实际容量被超出。提前把 Latch 数到零也不会自动产生任何任务结果。

## Conclusion · 计数器不会证明业务正确

模型只含三个逻辑任务、公平常规 acquire 与确定的结果，不涵盖超时、可中断等待、多许可申请或其他同步器。新建实验实例只是重开场景，不是底层 API 支持重置。

Latch 适合一次性的完成协调；Semaphore 适合限制并行资源使用。设计时还应处理任务异常、许可泄漏与错误释放。
