## Problem · 一个慢请求不能由一张 CPU 图解释

同样的十二个请求，慢查询、CPU 工作过多、短命对象分配都可能增加延迟，却应留下不同证据。诊断要先识别时间和资源花在哪里，再改变对应因素。

## Why · 可观测性是一组可关联的记录

Metrics 概括速率、错误、延迟和资源压力；Trace 记录某次请求经过的阶段；带 trace id 的日志可记录离散事件。线程快照区分 RUNNABLE 与等待，CPU profile 展示实际执行热点，堆和 GC 记录展示分配、停顿与存活压力。

真实系统要用一致身份关联这些信号，并考虑采样、时钟误差、标签基数和隐私。本课让全部证据来自同一执行轨迹，避免互不对应的静态示意数字。

## Mechanism · 从时点重建延迟

容量模型保存每请求到达、worker 开始、绑定结束、DB 排队/开始/结束、序列化和响应时点。单请求 Trace 区分排队与执行，不把别的请求时间加进来。CPU 样本只计实际 JVM 服务步骤，数据库外部工作不能因为耗时长就变成 Java CPU 热点。

指定时隙的线程表来自真实 worker 状态，堆曲线显示同一批请求的分配和回收。GC 后仍存在的活跃请求不是“回收器失效”，它们仍被业务持有。真实内存泄漏还需要 GC Roots 保留路径和长期趋势，本课不凭单点堆高就作判断。

示例 SLO 要求 99% 请求在预算内成功；不达标包括拒绝和超过预算。p95 用最近秩法，错误预算消耗率用当前失败比例除以允许的 1%。十二请求是有限实验样本，不能直接推广为稳定生产统计或告警窗口。

## Experiment · 让证据和修复对应

1. 默认慢查询场景运行基线，采集延迟/资源指标。
2. 查看时隙 5 的线程、request-1 Trace、CPU 样本和堆/GC 时序，发现 DB 等待与低 CPU 使用并存。
3. 先只增加 worker 复测，检查它是否改变真实瓶颈与结果。
4. 选择索引减少查询工作，用相同输入复测；p95 和预算不达标数下降，业务结果与接纳量不变，达到目标。
5. 切换 CPU 场景，减少绑定工作；切换 GC 场景，减少请求分配。每次重新采集对应证据，不把上一场景的结论直接套过来。

## Conclusion · 故障结论需要可反驳的验证

这是确定性模拟记录，不运行真实 OpenTelemetry、JFR、async-profiler 或堆分析器。无并行 Span 汇总、分布式时钟校正或真实生产流量。

提出能被测量反驳的解释，控制变量改变它，再核对结果、尾延迟、资源和错误预算。如果指标改善来自拒绝更多请求，或样本范围改变，就不能宣布同等负载下的性能问题已解决。
