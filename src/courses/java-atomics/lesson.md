## Problem · 可见的值仍可能被旧计算覆盖

共享 counter 初始为 0，T1 和 T2 各做一次 counter++。两个线程先读 0，分别计算 1，然后写回 1。每个读取都可以是当时最新的值，结果仍少了一次更新。

## Why · 生命周期与内存顺序解决不同问题

Thread.start 启动一个新执行路径，同一个 Thread 不能再次 start。start 前的动作 happens-before 新线程中的动作；另一线程成功从 join 返回后，可观察被等待线程的已完成动作。对尚未启动的 Thread 调用 join 可以直接返回，不能当作任务已运行的证据。

volatile 写与后续相应读取建立顺序保证，适合状态发布。本课把每次读写排入一个确定的顺序，仍能复现复合自增丢失，说明问题不需要诉诸“读到了脏缓存”。完整发布语义见 JMM 课程。

## Mechanism · 原子条件更新和重试

AtomicInteger 的 compareAndSet(expected, update) 原子地比较当前值并按条件写入。两线程读到 0 时，只有一次 CAS(0,1) 成功；失败者重新读取 1，计算 2，再尝试 CAS(1,2)。不能无条件重复使用过时的 expected 与候选值。

ABA 表示 A 被改为 B 又回到 A。只比较值无法发现中间变化。实验的带版本模式同时比较逻辑值和版本；实际 AtomicStampedReference 比较的是引用身份与 stamp，不能把这里的整数值比较直接当作它的完整 API。版本也需要正确维护，不能无限忽略溢出或复用。

interrupt 设置请求标志，不会强行撤销已执行动作。本任务在下一个步骤主动检查标志并退出；Thread.interrupted() 检查并清除当前线程的标志，与不清除标志的 isInterrupted() 不同。

## Experiment · 保留同样输入，改变更新边界

1. 默认 volatile 模式，T1 start 后执行一次读；切换 T2，也 start 并读。再让两线程各执行一次写，得到 1，提交次数为 2。
2. 切换 CAS 创建新场景。重复先读后写，第二个写失败；让失败线程再执行读、写，得到 2。main join 已终止的线程。
3. 切换带版本 CAS。启动当前线程并读，插入 A→B→A，再尝试写。值虽然回到 0，版本已经变化，写入失败，达到目标。
4. 独立重置后启动线程并中断，观察尚未立即终止；执行下一步让任务协作退出。另开一次尝试清除标志，再继续计算。

## Conclusion · 原子性需要明确覆盖范围

模型只有两个线程、每线程一次自增，不模拟硬件缓存、弱 CAS 的伪失败、stamp 回绕或真实调度。普通模式的版本仅是教学记录，并未参与比较。

CAS 不自动解决任意业务事务，也不保证线程永不饥饿。选择 Atomic、锁或更高层容器时，先找出必须作为整体生效的动作，再检查失败与取消路径。
