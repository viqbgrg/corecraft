## Problem · 加载成功不等于方法已经执行

类中有普通静态字段 `static int seed = 7`，方法 sum 返回 seed 加 5。仅加载类、准备字段、执行初始化、运行方法，是四件不同的事。

若把它们合并成“JVM 把类放进内存”，就很难解释 VerifyError、初始化失败或某一区域的内存耗尽。

## Why · JVM 架构把类型、执行和存储连接起来

类加载子系统读取定义并建立运行时类型。执行引擎可解释字节码或运行 JIT 编译代码；GC 管理堆中不再需要的对象，JNI 等机制连接本地代码。

线程有各自的 PC、Java 栈与方法帧；帧包含局部变量、操作数栈及方法执行相关信息。Heap 在逻辑上共享。Method Area 是规范中的逻辑概念，HotSpot 的类元数据通常存放在本地 Metaspace；运行时常量池属于类的运行时结构。java.lang.Class 对象、静态字段的具体存储和实现版本有关，不能把所有类相关内容都画成 Metaspace 内的一张表。本课单独展示静态值，不宣称其物理地址。

## Mechanism · 类型检查发生在数值运算之前

本课固定流程为加载 → 验证 → 准备 → 解析 → 初始化。验证器实际追踪直线方法的类型栈，检查 iadd 的两个 int 输入、局部变量初始化与返回类型。它不运行加法。错误的 areturn 在 int 栈值上失败，执行器不能进入方法。

准备为普通静态 int 建立 0，初始化执行 seed=7。这里没有 ConstantValue 属性对应的编译期常量；真实 JVM 可在不同时间解析符号引用，本模型选择提前解析。初始化失败使当前加载器中的这个类进入错误状态，首次主动使用报 ExceptionInInitializerError，后续使用可报 NoClassDefFoundError，而不是重新正常执行初始化器。

初始化完成后，getstatic、bipush、iadd、istore_0、iload_0、ireturn 实际改变 PC、操作数栈与局部值。实例分配进入另一张堆表。对象布局采用经典 64 位头、8 B 对齐；一个 int 与一个引用，在两个压缩机制都开启的示意配置下占 24 B，在宽指针配置下占 32 B。

## Experiment · 分开观察四类状态

1. 加载并验证，观察类型栈证据；此时 seed 尚未准备。
2. prepare 后 seed=0，resolve 后仍为 0；initialize 后变成 7。再次主动使用不增加成功初始化次数。
3. 在堆分配对象，查看头、字段和对齐填充，再比较两种配置。
4. 逐步解释执行：栈依次包含 [7]、[7,5]、[12]；存入 local0，读取后返回 12，完成目标。
5. 重置并选择错误 areturn，验证失败发生在执行之前；再试依赖缺失和初始化器抛错，核对错误阶段。
6. 正常场景连续分配到堆容量耗尽，观察 Heap 错误不会让 Metaspace 的示意数值自动增长。

## Conclusion · 规范区域与实现布局要分别说明

验证器只支持直线子集，没有 .class 解析、分支合流、完整类型层级或构造器未初始化对象规则。64 B 元数据与 128 B 堆只是教学容量，PC 按教学指令索引显示，不是字节偏移。

布局未模拟真实字段重排、TLAB、compact object headers 或独立的压缩开关；普通引用压缩与类指针压缩在实际 VM 中是不同机制。方法返回后界面保留帧的观察快照，不表示该帧仍活动。

参考 [JVMS 运行时结构](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html)，再用 GC 与 JIT 课程解释对象生命周期和执行优化。
