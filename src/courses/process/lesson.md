## Problem · 资源有限，任务很多

如果一个线程等待磁盘时一直占着 CPU，其他已经准备好的线程就只能干等。我们需要让 CPU 在有能力继续运行的执行流之间切换。

## Why · 分开“拥有什么”和“执行到哪里”

进程提供资源与隔离边界，线程承载执行流。Process A 的 Thread 1、Thread 2 共享同一个计数器，却各自拥有私有栈帧。Process B 的 Thread 3 无法直接改变 A 的计数器。

可以先把进程理解为一个运行中的程序及其资源，把线程理解为其中一条执行路线。同一进程的线程通常共享地址空间与打开的文件等资源，但需要分别记住下一步执行位置和方法调用现场。

本实验把这些状态缩小为两种计数：**进程共享计数**记录这个进程的线程总共执行了多少步，**线程私有计数**只记录本线程的步数。T1 与 T2 的私有计数可以都为 1，而 Process A 的共享计数已经为 2。

这里的“私有栈”强调每个线程有自己的调用现场，不是说线程之间存在进程级的内存隔离；同一进程内共享数据的正确访问仍然需要同步规则。

## Mechanism · 状态决定是否能调度

**Ready** 有资格运行；**Running** 正占用 CPU；**Blocked** 在本模型中表示等待 IO；**Waiting** 表示等待条件通知。操作系统中的等待分类和命名可能不同，这里为教学分别展示。

时间片用完或主动等待时，保存当前 PC / 栈，再恢复另一线程。完成 IO 使线程回到 Ready，而不是保证立即 Running。

### 按事件追踪状态

| 原状态  | 事件                 | 新状态  |
| ------- | -------------------- | ------- |
| Ready   | 被调度器选中         | Running |
| Running | 时间片耗尽或手动轮转 | Ready   |
| Running | 发起需要等待的 IO    | Blocked |
| Blocked | 对应 IO 完成         | Ready   |
| Running | 等待条件             | Waiting |
| Waiting | 收到条件通知         | Ready   |

Ready 表示有工作可做、正在等 CPU；Blocked / Waiting 表示当前还缺少继续执行的条件。把未就绪线程反复排上 CPU，不会让它的 IO 自动完成。本模型若没有任何 Ready 线程，CPU 会空闲，直到你完成 IO 或发出通知后再次调度。

### 上下文切换保存的是什么

T1 执行到 PC = 1 时等待 IO，切换到 T2 后，T1 的 PC 和私有计数不会归零。调度器再次选中 T1 时，恢复的是这个暂停点，下一次执行后 PC 变成 2。进程共享数据则一直保留，其他同进程线程可能已修改它。

本模型默认时间片为 3 步。运行线程每执行一步，就消耗一份时间片；耗尽后进入就绪队列尾部，再选队首。调度与执行是两种动作，点击“切换到下一线程”本身不会让业务计数增加。

## Experiment · 让等待变得可见

1. 重置并保留时间片 3，点击“调度 Ready 线程”，T1 开始运行。点击一次“执行一步”：T1 的 PC 和私有计数都为 1，Process A 共享计数为 1。
2. 点击“当前线程等待 IO”，T1 进入 Blocked，T2 自动接手 CPU。执行一步后，T2 的私有计数为 1，Process A 共享计数为 2，T1 的现场仍保留。
3. 确认“唤醒目标”为 T1，再点击“完成目标 IO”。T1 变为 Ready，**当前运行的仍是 T2**。这时已完成阻塞、唤醒和切换，基础实验目标达成。
4. 点击“切换到下一线程”，轮到 T3；执行一步，Process B 共享计数为 1，A 仍为 2。再切换到 T1，执行一步，T1 的 PC 从 1 变为 2，A 共享计数变为 3。
5. 选做：重置，将时间片改成 1，调度后连续执行，观察 T1、T2、T3 每步轮转。另做一次“当前线程等待条件 → 通知目标线程”，对比它与 IO 完成的唤醒入口。

每次记录 **Running、Ready Queue、目标线程的 PC / 私有计数、所属进程的共享计数**。这能分清 CPU 归谁使用、现场归谁保存，以及数据属于哪个共享范围。

## Conclusion · 并发不等于并行

这是单核轮转模型，同一时刻只执行一个线程。每个微步骤将共享与局部计数各加一，栈中显示的是局部计数所在的简化栈帧。真实的上下文还包含更多寄存器、内核状态，进程切换也可能涉及地址空间；本实验不模拟数据竞争或多核并行。

自检：T1 的 IO 完成后为什么没有马上运行？因为事件只让它具备运行资格，调度器还要在多个 Ready 线程之间作选择。并发描述多个任务在一段时间内交替推进；并行还需要同一时刻有多个执行资源。

增加线程不会自动增加 CPU 算力，频繁切换也需要代价。下一步的 CPU 调度课程会在相同任务上比较等待、响应和周转时间；Java 并发课程再展开共享数据需要的同步机制。
