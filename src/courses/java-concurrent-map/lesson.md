## Problem · 容器没有损坏，数字仍然少了

T1、T2 都从 ConcurrentHashMap 读取 A=0，再各自 put(A,1)。Map 内部结构依然正确，结果却只增加一次。容器调用安全与业务复合操作原子性不是同一保证。

## Why · 并发范围越大，互相等待越多

ConcurrentHashMap 允许多个线程使用，不接受 null 键或值。compute 可以在键的原子更新范围内执行回调，但回调应简短，避免递归修改造成的问题。不同键也可能散列到同一桶，因而产生实现层面的竞争。

## Mechanism · 更新边界与扩容路径

本课用 Java String 哈希和容量为二的幂的桶定位。A 与 E 在初始四桶表碰撞，B 位于另一桶。naive 操作保存 get 的局部值，稍后 put 时即使等待过桶锁，也不会自动重读。compute 先获得桶写锁，再读取最新值并提交加一，之后释放。

get 观察已提交条目，不获得教学桶写锁。某键的完成更新与读取该更新结果的访问之间有相应可见性保证；这不提供跨整个 Map 的原子快照。

扩容先建立双倍容量表，逐个旧桶搬迁。搬迁后清空旧条目并安装 Forwarding 标记，后续访问沿标记进入新表。被 compute 持有的桶暂不能搬迁，其他桶继续工作；全部旧桶完成后发布新根。操作记住自己的键，不会因为用户改输入框而悄悄换目标。

## Experiment · 从丢失更新到迁移中读取

1. T1、T2 都开始默认 get + put，再各推进一次，A 从 0 变成 1，已有两次提交。
2. 改为 compute，让 T1 开始，T2 开始并等待。T1 提交 A=2；T2 重试获取并读 2，再推进提交 A=3。
3. 开始扩容，迁移旧桶 0 和 1。读取 A，路径会经过旧表标记进入新表，值仍为 3。
4. 迁移桶 2、3，新表成为根，达到目标。
5. 独立重开，同时计算 A、E、B，检查碰撞等待；在持有 A 桶时尝试迁移，完成回调后重试。连续扩容两轮确认条目不重复或丢失。

## Conclusion · 结构安全需要与应用协议组合

模型模拟链式桶、写入互斥与 Forwarding，不逐行复刻 OpenJDK；省略空桶 CAS、树桶、size 计数、协作 transfer 和弱一致迭代器。表最多十六桶、十二个键，迁移操作逐桶原子执行。

需要复合计数时选适合的原子 API；涉及多个键或外部副作用时，单次 compute 并不等于全局事务。
