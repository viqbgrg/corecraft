## Problem · 等待数据，不能一直占着锁

T1 持有锁，但单槽缓冲没有数据。如果它占锁忙等，T2 无法进入临界区生产。T1 需要释放锁并等待，同时保证检查状态和进入等待之间不会漏掉正确的通知。

## Why · 锁与条件共同表达协议

synchronized 关联对象监视器，具有互斥和可重入语义。Object.wait、notify 要求持有该监视器。ReentrantLock 是显式锁，常在 try/finally 中 unlock；它基于 AQS，可创建 Condition 并选择公平策略。synchronized 的内部实现不是 AQS。

## Mechanism · 从等待条件到重新争用锁

ReentrantLock 的独占状态记录重入次数，owner 标识持有线程。AQS 同步队列保存尚不能获取锁的请求。Condition 等待集合保存等待某个谓词改变的线程，它与同步队列承担不同职责。

T1 两次 lock 后 await，保存计数 2，释放全部持有并进入条件集合。T2 lock、写入数据、signal，只把一个等待者转入重新竞争锁的位置；T2 仍是 owner。T2 unlock 后 T1 才可获取并恢复计数 2，await 返回后检查 while (!ready)。

伪唤醒没有保证 ready 变为 true。即使是正常 signal，也可能有其他消费者先取走数据，因此 while 比 if 更合适。公平锁约束本课常规获取路径的插队；非公平锁允许新尝试抢先。实际 ReentrantLock 的无参 tryLock 有公平策略例外，公平也不等于操作系统公平调度。

## Experiment · 通知、获取、消费三个时点

1. T1 获取两次，执行 while 检查并 await。持有计数归零，条件集合保存 2。
2. T2 获取锁、生产并 signal。条件集合变空，T1 进入同步队列，owner 仍为 T2。
3. T1 尝试获取，确认仍不能进入。T2 释放一次后，T1 再获取，计数恢复为 2。
4. T1 检查并消费，释放两次；所有权与等待集合均清空，达到目标。
5. 新建场景让 T1 等待，注入伪唤醒再尝试获取，观察 while 使它再次等待。切换 monitor 模式对照同样协议，但不要从展示顺序推断 FIFO 保证。

## Conclusion · 等待协议必须连同失败路径理解

本课模拟单锁、单条件和单槽数据，不实现底层 park、自旋、超时、中断、多个 Condition 或锁优化。错误线程解锁与通知会被拒绝；等待者不会因为按钮选择变化自动获得锁。

锁保护共享状态，条件等待表达“现在还不能继续”。把谓词写清楚，再决定谁修改、谁检查、谁通知，比背诵锁的名字更有用。
